Smart Turbine Health Analytics API

This document provides a complete technical guide for the API, designed for managing turbine metadata and analyzing sensor telemetry data from naval propulsion plants. It covers all available endpoints, data models, and the methodologies behind the analytical calculations.

Base URL: http://127.0.0.1:8000

API Version: 5.0.0

Analytics & Formulas Deep Dive

Derived features are the most powerful aspect of this API. They are not measured by a single sensor but are calculated by combining multiple sensor inputs to provide a deeper insight into the engine's thermodynamic condition.

Pressure Ratio (πₚ)

The fundamental measure of the compressor's work. It quantifies how much the air pressure is increased from the inlet to the outlet.

Calculation:

  • P₂: Compressor Outlet Pressure (bar)
  • P₁: Compressor Inlet Pressure (bar)

Thermal Efficiency (ηₜₕ)

A theoretical measure of how efficiently the turbine converts fuel's heat energy into useful work, based on the ideal Brayton Cycle.

Calculation:

  • πₚ: The Pressure Ratio calculated above.
  • γ (Gamma): The heat capacity ratio for air, a constant value of 1.4.

Compressor Isentropic Efficiency (η꜀)

The most direct indicator of the compressor's health. It compares the actual energy used to compress air with the ideal (frictionless) energy required.

Calculation (Two Steps):

  1. First, calculate the Ideal Outlet Temperature (T₂ₛ):
  2. Then, calculate the efficiency by comparing the ideal temperature rise to the actual rise:
    • T₁: Actual Compressor Inlet Temperature (from sensor `t1`).
    • T₂: Actual Compressor Outlet Temperature (from sensor `t2`).
    • T₂ₛ: The ideal (Isentropic) Outlet Temperature calculated in step 1.
    • Note: All temperatures are converted to Kelvin (°C + 273.15) for calculations.

ETL Pipeline & Anomaly Detection

This section details the automated **Extract, Transform, Load (ETL)** pipeline triggered by the POST /data/upload-data/{turbine_id} endpoint. This pipeline is crucial for converting raw, potentially unreliable sensor data into a clean, analysis-ready format and for automatically detecting operational anomalies.

Step 1: Extract (E)

The process begins by extracting data from the uploaded CSV file. The API validates the file type and parses the content into a structured DataFrame, which is an in-memory table.

  • Action: Reads the uploaded `.csv` file.
  • Why: To convert the raw text data into a structured format that can be programmatically manipulated.
  • Validation: Ensures the file has a `.csv` extension and that all required sensor columns are present.

Step 2: Transform (T)

This is the core data processing stage, involving several sub-steps to clean and enrich the data.

A. Column Renaming

The original CSV headers are verbose (e.g., "HP Turbine exit temperature (T48) [°C]"). They are renamed to simple, standardized names (e.g., "t48").

Why?

  • Consistency: Ensures predictable column names for all downstream calculations and database storage.
  • Simplicity: Makes coding and querying far easier and less error-prone.

B. Outlier Mitigation (IQR Capping)

Sensor data can contain erroneous spikes due to electrical interference or sensor malfunction. This pipeline identifies and corrects these outliers using the Interquartile Range (IQR) method.

Why not just delete outliers?

  • In time-series data, each point is part of a sequence. Removing a point creates a gap and distorts time-based calculations like moving averages. Capping (or flooring) brings the value back to a plausible maximum (or minimum) without breaking the sequence.

How it Works:

Any value above the Upper Bound is set *to* the Upper Bound. Any value below is set *to* the Lower Bound. [Image of Interquartile range boxplot]

C. Noise Reduction (Smoothing)

Raw sensor data is often "noisy." A 3-point moving average is applied to smooth out these random fluctuations.

Why?

  • This filtering reveals the true underlying trend in the data, making it easier for both humans and algorithms to spot meaningful changes rather than reacting to insignificant noise.

Step 3: Automated Anomaly Detection

After cleaning, each row of data is checked against a set of predefined operational thresholds. If a value exceeds a threshold, an anomaly is automatically logged in the `anomaly_alerts` table.

Thresholds & Significance:

High Severity: Critical Turbine Exit Temperature

Threshold: `t48 > 950` °C

Meaning: This is a critical alert. The turbine's hot section is under extreme thermal stress. Sustained operation above this limit can lead to rapid material degradation, blade damage, and potentially catastrophic engine failure.

Medium Severity: Component Decay

Threshold: `decay_coeff_turbine < 0.96` or `decay_coeff_comp < 0.96`

Meaning: These coefficients represent the health of the turbine and compressor relative to a new component (1.0 = perfect health). A value below 0.96 indicates a significant loss of performance due to factors like fouling, erosion, or wear. This is a strong signal for upcoming maintenance.

Low Severity: Low Pressure Ratio at Speed

Threshold: `pressure_ratio < 9.0` (only when `gtn > 1500` RPM)

Meaning: When the turbine is running at speed, the compressor should be generating a high pressure ratio. If it fails to do so, it indicates inefficiency. This is often the earliest, most subtle sign of compressor fouling before it impacts other parameters.

Step 4: Load (L)

Finally, the cleaned, transformed, and analyzed data is loaded into the `sensor_readings` database table for the specified turbine.

  • Action: Appends the processed DataFrame to the SQL table.
  • Why: This persists the high-quality data, making it available for fast and efficient querying by all other API endpoints.

Turbine Management

POST/turbines

Creates a new turbine record in the `turbine_metadata` table. This is the first step before uploading sensor data for a new turbine.

Request Body

{
  "location": "North Sea Platform Alpha",
  "manufacturer": "Siemens",
  "model": "SGT-400"
}

Responses

201 Created:

{
  "location": "North Sea Platform Alpha", "manufacturer": "Siemens", "model": "SGT-400", "turbine_id": 4
}

GET/turbines

Retrieves a list of all turbines registered in the `turbine_metadata` table.

Responses

200 OK:

[
  { "location": "Singapore Port", "manufacturer": "GE", "model": "GTX-1000", "turbine_id": 1 },
  { "location": "Singapore Port", "manufacturer": "Siemens", "model": "ST-2000", "turbine_id": 2 }
]

GET/turbines/{turbine_id}

Retrieves the detailed metadata for a single turbine identified by its ID.

Responses

200 OK:

{
  "location": "Singapore Port", "manufacturer": "GE", "model": "GTX-1000", "turbine_id": 1
}

PUT/turbines/{turbine_id}

Updates the metadata for an existing turbine.

Request Body

{ "location": "Atlantic Relay Station", "manufacturer": "General Electric", "model": "GTX-1000 Rev.2" }

Data & Analytics

POST/data/upload-data/{turbine_id}

Performs a full ETL pipeline on a batch of sensor data from a CSV file. It cleans, processes, and loads the data into the database for the specified turbine. See the ETL & Anomaly Detection section for a full breakdown.

POST/data/sensor-reading/{turbine_id}

Logs a single, real-time sensor reading and automatically checks it against thresholds to log anomalies.

GET/data/sensor-metrics/{turbine_id}

Retrieves the most recent sensor readings for a turbine, ideal for real-time dashboards.

GET/data/health-summary

Provides a high-level, lifetime-to-date scorecard for each turbine, including calculated performance and efficiency metrics.

POST/data/analytics-report

Returns a detailed statistical report (min, avg, max) for specified turbines over a date range. If dates are omitted, it analyzes the entire data history.

POST/data/anomaly-alerts

Manually logs a new anomaly alert.

GET/data/anomaly-alerts

Retrieves a list of logged anomaly alerts, with optional filters for `turbine_id` and a date range.
